## 2. 문제와 목표

**상황**: 정찰 자산(드론·로봇)이 대상을 원격 관찰. 접근 전에 "항복 의사가 있는지 / 항복하는 척 공격을 준비하는지"를 영상만으로 가려야 한다.

**출력: 사람마다 3상태** (우선순위 DANGER > UNKNOWN > SURRENDER)

| 상태 | 조건 | 색 |
|---|---|---|
| DANGER | 한 손이라도 가려짐(손목 안 보임 / 1초 연속 손 못 찾음) **또는** 물체 들고 있음 | 빨강 |
| SURRENDER | 양손 모두 펴짐 + 물체 없음 + 양 손목이 어깨보다 위 | 초록 |
| UNKNOWN | 그 외(손 내림·주먹·손목 화면 밖·인식 실패) | 노랑 |

그림: 맥 웹캠 실측 HUD 4장(`images/hud_*.png`) — SURRENDER(양손 OPEN·어깨 위) / DANGER(손과 겹친 검출 → OBJECT(remote?)·윤곽) / DANGER(등 뒤 손 = 손목 안 보임, 박스 없음) / UNKNOWN(양손 CLOSED·어깨 아래)

> 노트 (40초): "판단은 '손'에 집중했습니다. 손이 안 보이거나 뭔가 쥐고 있으면 위험, 양손을 펴서 어깨 위로 들었으면 항복, 나머지는 보류입니다. 위험을 놓치는 비용이 가장 크니까 DANGER를 먼저 묻습니다. 상태는 5프레임 연속 같아야 바뀌고, 잠깐 가려지면 Kalman 예측으로 최대 30프레임 위치와 직전 상태를 유지합니다."
>
> 예상 질문: **왜 UNKNOWN이 필요한가?** → 손을 내리고 있거나 손 인식이 실패한 상태는 '위험'도 '항복'도 아님. 둘 중 하나로 몰면 오판이 됨. 접근 여부를 보류하라는 신호.
> **SURRENDER에 손 높이 조건을 왜 넣었나?** → 손만 펴고 내린 자세는 항복 신호가 아님. 손목 y < 어깨 평균 y 를 추가(`are_hands_raised`).

## 3. 파이프라인 — 9개 파일, 한 프레임의 흐름

그림: 파일 파이프라인(파랑 = 인식·추적, 노랑 = 판단, 초록 = 그리기)

카메라 1280x720 → `preprocess` 640폭 축소 → `person_detector` Pose(최대 3명)·사람 판정 → `target_tracker` 사람별 Kalman + ID → `hand_analyzer` 손 crop → HandLandmarker → `held_object` EfficientDet 전체 프레임 검출 ↔ 손 박스 겹침 → `threat_classifier` 규칙 + 디바운스 → `hud` overlay. 조립은 `main.process_frame`.

> 노트 (40초): "파일은 역할 하나씩입니다. 모델을 들고 있는 것만 클래스(PersonDetector·HandAnalyzer·HeldObjectDetector·트래커), 나머지는 순수 함수라 카메라 없이 테스트됩니다(81개). process_frame이 한 프레임을 이 순서로 조립합니다."
>
> 예상 질문: **왜 640으로 줄이나?** → 픽셀 수 1/4, Pose·검출기 입력은 어차피 256~320px로 내부 축소되므로 정확도 손실 거의 없음. 모든 픽셀 임계값(어깨 40px 등)은 640폭 기준.
> **Pose와 Hand를 따로 쓰는 이유?** → Pose 손목 좌표는 손가락 펴짐을 모름. 손목 주변만 잘라 HandLandmarker 21점으로 손가락 각도를 잼.

## 4. 요구 기술 8개 ↔ 코드 위치

| 기술 | 함수 | 파일 |
|---|---|---|
| 이미지 조정 | `resize_for_processing`, `crop_frame`, `locate_hand` | preprocess, hand_analyzer |
| 필터링 | `blur_frame` (GaussianBlur 5x5) | preprocess |
| 색공간 변환 | `convert_to_lab` (BGR→LAB), BGR→RGB (MediaPipe 입력) | preprocess 외 |
| Image Enhancement | `enhance_lightness` (L 채널 CLAHE) | preprocess |
| Color Segmentation | `find_object_contour` 안 `cv2.inRange` (a·b 중앙값 ±12) | held_object |
| Contour Detection | `find_object_contour` (open/close → findContours → 최대 면적) | held_object |
| 객체 추적 | `MultiTargetTracker`, `TargetTracker`, `create_kalman_filter` | target_tracker |
| 신체 인식 | `PersonDetector`, `is_human`, `HandAnalyzer`, `is_hand_open` | person_detector, hand_analyzer |
| 관계성 | `does_overlap_hand`, `apply_held_objects`, `classify_person`, `are_hands_raised` | held_object, main, threat_classifier |

> 노트 (30초): "강의에서 다룬 기술이 어디에 쓰였는지 표로 정리했습니다. 색 분할·윤곽은 검출기 박스 안에서 물체 영역만 정밀하게 남기는 단계이고, 관계성은 '객체↔손 겹침'과 '손목↔어깨 높이' 두 군데입니다."
>
> 예상 질문: **LAB를 쓴 이유?** → L(밝기)과 a·b(색)가 분리돼 조명이 바뀌어도 색 범위가 유지됨. CLAHE는 L에만 적용해 색 임계값에 영향 없음.
> **CLAHE가 실제로 뭘 바꾸나?** → 그늘진 손 안 물체의 L 대비를 올림. 테스트에서 저대비 입력의 L 표준편차가 커지는지 확인.

## 5. 실시간을 위한 배분 — 무거운 일은 프레임마다 나눈다

그림: 프레임별 작업 배분(홀수 = 손, 짝수 = 물체) / 3명일 때 프레임당 모델 시간(전부 175ms → 최대 69ms)

맥(M2) 실측 프레임당: 카메라 읽기 13ms · Pose 24ms · EfficientDet 37ms(짝수 프레임만) · HandLandmarker 23ms/crop(홀수 프레임, 사람당 한 손씩 번갈아). 결과 10~15fps.

> 노트 (30초): "모델 세 개를 매 프레임 다 돌리면 3명일 때 175ms라 실시간이 안 됩니다. 물체 검출은 짝수 프레임, 손 분석은 홀수 프레임에 한 손씩 번갈아 돌리고 나머지는 직전 결과를 재사용합니다. 5프레임 디바운스가 있어서 한두 프레임 늦는 손 상태는 결과에 거의 영향이 없습니다."
>
> 예상 질문: **직전 결과 재사용이 판정을 틀리게 하지 않나?** → 한 손은 4프레임마다 갱신(≈0.27초). 디바운스 5프레임(≈0.33초)보다 짧아 상태 전환 지연이 1프레임 수준.
> **Jetson fps는?** → Orin Nano Super 실측 약 10fps(MAXN SUPER + `jetson_clocks`; 기본 25W 모드는 5fps). MediaPipe가 aarch64에서 CPU만 써서 클럭에 비례. 더 올리려면 `DETECT_EVERY_FRAMES`를 늘리거나 `pose_landmarker_lite`로 교체.

## 6. 객체 추적 — 사람마다 명찰(ID)을 유지한다

그림: 한 사람의 명찰 시간표(30프레임 ≈ 2초까지 예측) / 측정·예측·보정 점

- 몸 중심 = **어깨 중점**(엉덩이 포함 평균은 앉은 자세에서 엉덩이 visibility가 깜빡여 중심이 100px 점프 → ID 바뀜, 실측으로 교정)
- 사람별 `cv2.KalmanFilter`(등속 모델, 상태 x·y·vx·vy, 측정 x·y)
- 매칭: 이전 중심 ↔ 새 측정 거리가 가까운 쌍부터 짝짓기(greedy). 허용 거리 max(100px, 0.8×어깨 너비)
- 측정 없으면 예측으로 30프레임 버팀(PREDICTING, 점선 박스), 넘기면 삭제. ID 재사용 없음

> 노트 (35초): "Pose는 프레임마다 사람 목록 순서가 바뀔 수 있어서, '지난 프레임에 어디 있었나'로 같은 사람을 이어 붙입니다. 가까이 있는 사람은 화면에서 크게 움직이니까 허용 거리를 어깨 너비에 비례시켰습니다. 실측에서 어깨 160px 이상일 때 몸을 돌리자 ID가 1→6으로 바뀐 걸 보고 넣은 규칙입니다."
>
> 예상 질문: **Kalman이 꼭 필요한가?** → 잠깐 가려졌을 때 위치와 직전 상태를 유지하려면 예측이 필요. 없으면 가려질 때마다 새 ID·UNKNOWN으로 리셋.
> **greedy 매칭이 틀리는 경우?** → 두 사람이 교차할 때 가장 짧은 쌍을 먼저 잡아 뒤바뀔 수 있음(헝가리안 알고리즘이 정석). 최대 3명·시연 환경에선 충분.

## 7. 손 판정 — 어디를 얼마나 자르고, 무엇을 재나

그림: crop 반폭 = 어깨 너비 × 0.9 (40~200px) / 손 점 21개와 각도를 재는 관절

1. 손목 검사 순서: 화면 밖 → **OUT** / visibility < 0.5 → **HIDDEN** (순서를 바꾸면 화면 밖 손이 전부 위험으로 뜸)
2. crop 중심 = 손목·검지 중점, 반폭 = 어깨 너비 × 0.9 → 멀든 가깝든 손이 같은 비율로 들어옴
3. HandLandmarker 21점 → 검지~소지 둘째 마디 각도 모두 ≥ 160° → **OPEN**, 아니면 **CLOSED**, 못 찾으면 **NOT_FOUND**
4. NOT_FOUND 15프레임(≈1초) 연속 → **HIDDEN** (등 뒤 손도 Pose가 "보인다"고 추정하는 실측 사례 대응)

> 노트 (35초): "손 하나는 6가지 상태 중 하나가 됩니다. 각도는 정규화 좌표가 아니라 crop 크기를 곱한 픽셀로 잽니다. 가장자리에서 잘린 crop은 정사각형이 아니라서 정규화 좌표로 재면 각도가 틀어지기 때문입니다. 엄지는 각도 기준이 불안정해 뺐습니다."
>
> 예상 질문: **왜 0.9배인가?** → 편 손 길이가 어깨 너비의 절반 정도, 든 물체가 손 밖으로 튀어나오므로 넉넉히. 하한 40은 그보다 작으면 손 모델이 못 찾고, 상한 200은 옆 사람 손이 들어옴.
> **IMAGE 모드를 쓴 이유?** → 한 프레임에 사람 수×2개 crop을 따로 넣어야 하는데 VIDEO 모드는 같은 타임스탬프를 두 번 못 받음.

## 8. 물체 판별 — 세 번 바꾼 설계 결정

| ① 파란색 분할 | ② 손바닥 피부색 대비 | ③ 검출기 = "존재 감지기" (최종) |
|---|---|---|
| "파란 물건 = 무기 모형" inRange | 손바닥 안에 피부색과 다른 색이 있으면 물체 | EfficientDet-Lite0(COCO) 전체 프레임 → person 제외 검출이 손 박스와 20% 이상 겹치면 OBJECT |
| ✗ 파란 노트 b≈110이 임계값 경계, 물체가 crop 밖으로 나감 | ✗ 물체를 쥐면 손 랜드마크가 주먹(피부) 위에 놓이고 물체는 손 밖. 영역을 넓히면 옷·벽이 들어와 빈 주먹과 구분 불가 | ✓ 클래스는 거의 틀리지만(펜→toothbrush) "손 근처에 뭔가 있다"는 잘 잡힘. 활짝 편 손은 제외, 검출 끊겨도 10프레임 유지 |

최종: 검출 박스(거침) 안에서 블러 → LAB → CLAHE → 중심부 a·b 중앙값 ±12 inRange → open/close → 최대 윤곽(정밀) → HUD 자홍 윤곽

> 노트 (40초): "제일 많이 바꾼 부분입니다. 카메라 앞에서 직접 동작하면서 수치를 모아 비교했습니다. 접근 전 안전 판단에는 '무엇인지'보다 '들렸는지'가 중요하다고 보고, 검출기를 분류기가 아니라 존재 감지기로 썼습니다. 점수 임계값 0.25는 0.2면 빈손 오검출 8~10%, 0.3이면 펜 검출률이 84→49%로 떨어져서 그 사이로 잡았습니다."
>
> 예상 질문: **위협 물체만 골라내면 안 되나?** → 경량 모델의 클래스가 신뢰 불가. 더 큰 모델(Lite2·YOLO)로 바꾸면 화이트리스트(knife·scissors) 가능 — 확장 항목.
> **OPEN 손을 제외하는 근거?** → 활짝 편 손은 물건을 쥘 수 없음. 빈손을 펴 들었을 때 remote 오검출로 DANGER가 뜨던 것(실측 14%)을 막음.

**한계**
- 손 뒤 배경 물체(침대·마우스)가 "든 물체"로 잡힘 → 겹침 기준을 손 박스 자체로 좁히고 시연은 배경을 비움
  - 그림: 실측 오탐(`images/hud_false_positive_bed.png`) — 내린 손이 침대와 겹쳐 OBJECT(bed?) → DANGER

- 어깨 너비 < 40px(약 7m 이상)인 사람은 무시 (책상 위 소품 오검출 방지의 대가)
- Jetson Orin Nano Super 약 10fps(MAXN SUPER 전력 모드 필수, 기본 25W는 5fps) — 검출률 수치는 맥(M2) 기준

> 노트 (35초): "처음 서서 찍었을 때 SURRENDER가 0%였는데, 원인은 모델이 아니라 카메라 높이였습니다. 가슴 높이로 맞추니 1.5~2.5m 전 구간에서 양손 OPEN 97% 이상이 나왔습니다. 한계는 숨기지 않고 README에 수치와 함께 적었습니다."
>
> 예상 질문: **얇은 종이가 43%인 이유?** → EfficientDet-Lite0가 얇고 밝은 물체에 약함. 모델 한계이며 규칙으로는 못 올림.
> **왜 어깨 40px인가?** → 마우스·케이블을 사람으로 잡은 사례의 어깨 너비가 10~39px, 실제 사람은 2~3m에서 80~150px. 손 crop 최소 반폭과 같은 값.

## 10. 창의성·확장, 시연

**창의성**
- 사람(Pose) → 손(Hand) → 손 근처 물체(검출기+색 윤곽) → 손 높이까지 **한 판정으로** 묶어 "위협 / 보류 / 협조"라는 의미 있는 결론
- 경량 검출기의 약점(클래스 오류)을 규칙 설계로 피함: **분류기가 아니라 존재 감지기**
- 손 crop·매칭 거리를 **어깨 너비에 비례** → 거리 불변
- 다중 인원: 사람별 Kalman + ID + 상태 디바운스, `N PERSONS k DANGER` 요약

**확장**: EfficientDet-Lite2·YOLO로 위협 물체 화이트리스트 / 손바닥 방향(handedness·외적 부호) 조건 / Pose 속도 벡터로 접근·이탈 표시 / Jetson TensorRT

**시연 (2m, 가슴 높이)**: ① 양손 펴 들기 → SURRENDER ② 펜·폰 들기 → DANGER ③ 한 손 등 뒤 → DANGER ④ 손 내리고 서기 → UNKNOWN

**AI 활용**: 설계(시나리오·3상태·손 소분류·물체 판별 교체·수치)는 본인이 질문-답 방식으로 결정, 코드 초안은 AI가 모듈 단위로 작성 → 본인이 함수 단위로 검토. 테스트(assertion) 먼저 → 구현. 81개 통과.
